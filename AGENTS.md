# Разработка приложения

Ответы, спецификации и отчёты пиши на русском; API, команды и технические идентификаторы сохраняй в оригинале.

## Рабочий процесс

- Для нового поведения, изменения контракта, схемы данных или архитектуры используй `$sdd-change`. Не начинай реализацию, пока цель, границы и проверяемые сценарии не согласованы.
- Небольшая локальная правка без изменения наблюдаемого поведения может выполняться напрямую. Зафиксируй, почему полная change-spec избыточна, и всё равно выполни релевантные проверки.
- OpenSpec — движок change-артефактов, а не замена инженерного решения. Не считай пользовательскую гипотезу обязательным требованием без явного подтверждения.
- Для Rust/Axum/Tauri кода используй `$rust-app-engineering` и профиль из [.sdd/stack.md](.sdd/stack.md).
- Для задач, явно затрагивающих shadcn-vue, или после подтверждения существующей Vue/shadcn-vue конфигурации используй `$shadcn-vue-engineering`. Не выбирай его только из-за Vue, Tailwind или общего `components.json`.
- Перед завершением изменения используй `$quality-gate`. Не объявляй непроверенный результат работающим.
- Все OpenSpec-команды выполняй через `bun run tools/openspec.ts`; не используй bare `openspec` из `PATH`.
- Архивируй OpenSpec change только через `$safe-archive-change`; прямой вызов archive и upstream archive skill не обходят обязательные проверки проекта.

## Инженерные границы

- Сначала изучай существующий код, спецификации и lockfiles. Не обновляй зависимости и не меняй публичные контракты без необходимости, отражённой в change-spec.
- Отделяй доменную модель от HTTP/Tauri transport, persistence и UI. Зависимости должны направляться к доменному ядру.
- Ожидаемые ошибки моделируй типами; не используй panic, `unwrap()` или `expect()` в production request paths.
- Секреты, внутренние причины ошибок и SQL не должны попадать в клиентские ответы или git.
- Интеграции с PostgreSQL проверяй реальной PostgreSQL через testcontainers; mock не подтверждает SQL, миграции и транзакции.
- Сохраняй изменения узкими. Не форматируй и не переписывай несвязанные пользовательские файлы.

## Источники истины

- Живущие требования: `openspec/specs/`.
- Активные изменения: `openspec/changes/`.
- Стек и локальные решения: `.sdd/stack.md` и ADR проекта.
- Фактические версии: lockfiles и manifests проекта; значения из шаблона являются проверенной отправной точкой, а не разрешением на автоматическое обновление.
