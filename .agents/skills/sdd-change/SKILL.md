# SDD change

Сделай спецификацию рабочим контрактом между пользователем, кодом и проверками, не превращая процесс в самоцель.

## Выбор глубины

- Для нового поведения, изменения API/данных, архитектурного решения или многокомпонентной правки используй OpenSpec change.
- Для локального bugfix сначала зафиксируй воспроизводимое текущее и ожидаемое поведение. Полный design artifact нужен только если исправление меняет границы или требует выбора подхода.
- Для форматирования, переименования или очевидной механической правки можно обойти change, если публичное поведение не меняется.
- Если запрос является исследованием и выбор влияет на стоимость или архитектуру, сначала проведи исследование; не маскируй неизвестное фиктивной спецификацией.

## Работа с OpenSpec

Используй установленные OpenSpec skills вместо копирования их логики:

1. `$openspec-explore` — когда цель или вариант решения ещё не ясны.
2. `$openspec-propose` — создать proposal, delta specs, design и tasks до реализации.
3. `$openspec-update-change` — пересогласовать артефакты при новых фактах или изменении требований.
4. `$openspec-apply-change` — реализовать согласованные задачи.
5. `$openspec-sync-specs` — синхронизировать living specs, когда это нужно до архива.
6. `$safe-archive-change` — единственный разрешённый путь archive после обязательного quality gate. Upstream `openspec-archive-change` намеренно не устанавливается.

Не угадывай имя активного change: получи его из запроса или `bun run tools/openspec.ts list`. Все OpenSpec-команды выполняй только через repo-local pinned launcher. Не редактируй сгенерированные OpenSpec skills вручную; обновляй их выпуском wrapper.

## Инварианты

- Сценарий должен быть проверяемым по наблюдаемому результату, а не по предполагаемой реализации.
- Предпочтение пользователя не становится MUST без подтверждения.
- Реализация не должна незаметно расширять scope. При расхождении обнови change-артефакты и сообщи пользователю о существенном выборе.
- Для каждого изменённого контракта проследи цепочку: requirement → task → code → test/evidence.
- Архивирование означает завершённое и проверенное изменение, а не просто отсутствие незакрытых checkbox.
